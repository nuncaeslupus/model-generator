# Project-Agnostic Development Rules

**Purpose:** Ensure the model-generator skill remains completely reusable across any project.

**Last Updated:** 2026-01-17

---

## 🎯 Core Principle

> **The skill directory (`.agents/model-generator/`) must contain ZERO project-specific code.**
>
> Every template, script, and configuration must work for ANY project using the stack.

---

## ✅ DO - Project-Agnostic Patterns

### 1. Use Configurable Paths

**✅ GOOD:**

```python
# In generate.py
output_dir = project_root / config["paths"]["database_models"]
```

**❌ BAD:**

```python
# Hardcoded project structure
output_dir = project_root / "backend" / "src" / "database" / "models"
```

---

### 2. Generate Import Paths from File Paths

**✅ GOOD:**

```jinja2
{# In template - dynamic import from config #}
from {{ config.paths.database_models | path_to_import }}.enums import {{ enum_name }}
```

**❌ BAD:**

```jinja2
{# Hardcoded import path #}
from backend.src.database.models.enums import {{ enum_name }}
```

**Why:** Projects have different structures:

- Backend-only: `src/database/models/`
- Monorepo: `services/api/src/database/models/`
- Flat: `models/`

---

### 3. Reference Project Config, Not Stack Config

**✅ GOOD:**

```yaml
# In .model-generator.example.yaml (template for projects)
project:
  name: "Your Project"
  description: "Your project description"

stack: python-fastapi

paths:
  database_models: backend/src/database/models # User customizes
```

**❌ BAD:**

```yaml
# In stacks/python-fastapi/config.yaml
project:
  name: "Trading Kit" # Specific to one project
```

**Why:** Stack config should define HOW to generate, not WHAT to generate.

---

### 4. Use Path Variables in Templates

**✅ GOOD:**

```jinja2
{# Calculate base paths for imports #}
{% set db_models = config.paths.database_models | path_to_import %}
{% set api_base = config.paths.api_models | path_to_import | dirname %}

from {{ db_models }}.enums import UserStatus
from {{ api_base }}.validators import validate_email
```

**❌ BAD:**

```jinja2
from backend.src.database.models.enums import UserStatus
from backend.src.api.validators import validate_email
```

---

### 5. Document Multiple Project Structures

**✅ GOOD:**

```yaml
# In .model-generator.example.yaml

# Example 1: Full-stack project (default)
paths:
  database_models: backend/src/database/models
  api_models: backend/src/api/models

# Example 2: Backend-only
# paths:
#   database_models: src/database/models
#   api_models: src/api/models

# Example 3: Monorepo
# paths:
#   database_models: services/api/src/database/models
#   api_models: services/api/src/api/models
```

**❌ BAD:**

```yaml
# Only showing one structure
paths:
  database_models: backend/src/database/models
```

---

## ❌ DON'T - Project-Specific Anti-Patterns

### 1. Never Hardcode Directory Names

**❌ NEVER:**

```python
# These assume specific project structure
db_path = Path("backend/src/database")
api_path = Path("backend/src/api")
tests_path = Path("tests/contract")
```

**✅ INSTEAD:**

```python
db_path = project_root / config["paths"]["database_models"]
api_path = project_root / config["paths"]["api_models"]
tests_path = project_root / config["paths"]["api_tests"]
```

---

### 2. Never Hardcode Import Statements

**❌ NEVER:**

```python
# In config.yaml or templates
import: "from backend.src.api.validators import validate_email"
from backend.src.database.models.enums import UserStatus
```

**✅ INSTEAD:**

```python
# Use dynamic import generation
import: "from {{ validators_import }} import validate_email"
from {{ db_models_import }}.enums import UserStatus
```

---

### 3. Never Reference Specific Entity Names

**❌ NEVER:**

```python
# In skill code
if entity_name == "User":
    # Special handling for User entity
```

**✅ INSTEAD:**

```python
# Use generic patterns based on field types/attributes
if entity.get("is_auth_entity"):
    # Special handling for any auth entity
```

---

### 4. Never Assume Project Metadata

**❌ NEVER:**

```python
# In templates
"""
Trading Kit - Database Models
Copyright 2024 Trading Kit Team
"""
```

**✅ INSTEAD:**

```python
# Use project config
"""
{{ config.project.name }} - Database Models
Generated by model-generator v{{ config.stack.version }}
"""
```

## 🔍 Testing Project-Agnosticism

### Checklist Before Committing Changes

Run these checks to ensure no project-specific coupling:

```bash
# 1. Check for hardcoded paths
cd .agents/model-generator
grep -r "backend/src" . --exclude-dir=node_modules
grep -r "tests/contract" . --exclude-dir=node_modules
grep -r "trading" . --exclude-dir=node_modules -i

# Expected: No results (or only in documentation examples)

# 2. Check for hardcoded imports
grep -r "from backend\." stacks/python-fastapi/templates/
grep -r "from backend\." stacks/python-fastapi/config.yaml

# Expected: No results

# 3. Verify all paths come from config
grep -r "project_root /" scripts/ | grep -v "config\[\"paths\"\]"

# Expected: Only references that use config["paths"]
```

## 📚 Where to Put What

### Skill Directory (`.agents/model-generator/`)

**Contains:**

- ✅ Generic templates (use Jinja2 variables for everything)
- ✅ Generic scripts (use config for all paths)
- ✅ Stack configuration (type mappings, patterns, HOW to generate)
- ✅ Documentation (generic usage, not project-specific)
- ✅ Examples showing MULTIPLE project structures

**Never Contains:**

- ❌ Project-specific entity definitions
- ❌ Project name or metadata
- ❌ Hardcoded file paths
- ❌ Hardcoded import paths
- ❌ References to specific entities (User, Product, etc.)

---

### Project Root

**Contains:**

- ✅ `.model-generator.yaml` - Project-specific configuration
- ✅ `models/*.model.json` - Entity definitions for THIS project
- ✅ `models/_shared/enums.json` - Project's enums
- ✅ `models/_shared/constraints.json` - Project's constraints

---

## 🎓 When You Break The Rules

If you find yourself thinking:

> "I'll just hardcode this path for now and fix it later..."

**STOP.** That's how coupling happens.

### Instead:

1. **Ask:** "Could another project have a different structure here?"
2. **Make it configurable:** Add to project config
3. **Document:** Show examples in `.model-generator.example.yaml`
4. **Test:** Mentally run through 3 different project structures

---

## 🧪 Three-Structure Test

Before committing ANY change to the skill, mentally test it with these structures:

### Structure 1: Full-stack (default)

```
project/
├── backend/src/database/models/
├── backend/src/api/models/
└── tests/contract/api/
```

### Structure 2: Backend-only

```
project/
├── src/database/models/
├── src/api/models/
└── tests/api/
```

### Structure 3: Monorepo

```
project/
├── services/
│   └── api/
│       ├── src/database/models/
│       ├── src/api/models/
│       └── tests/api/
```

**Question:** Does your change work for ALL THREE without modification?

- ✅ YES → Good to commit
- ❌ NO → Make it configurable

---

## 🚨 Red Flags (Stop and Refactor)

If you see these in `.agents/model-generator/`, you have coupling:

1. **String literals with slashes:** `"backend/src"`, `"tests/contract"`
2. **Hardcoded imports:** `from backend.src.X import Y`
3. **Project names:** `"Trading Kit"`, `"MyApp"`
4. **Specific entity names:** `if entity == "User"`
5. **Absolute paths in examples:** Only show relative paths from project root

---

## 📖 Documentation Standards

### In Skill Documentation

**✅ DO:**

- Show generic examples with placeholders
- Demonstrate multiple project structures
- Use `your-project` or `example-app` in examples
- Explain WHY something is done, not just HOW

**❌ DON'T:**

- Use trading-kit specific examples
- Assume any particular directory structure
- Reference specific entities from trading-kit

### In Project Documentation

**✅ DO:**

- Reference how to use the skill in THIS project
- Show actual entity names and paths from trading-kit
- Link to skill docs for generic information

---

## 🔄 Review Checklist for PRs

Before merging changes to `.agents/model-generator/`:

- [ ] No hardcoded paths (backend/src, tests/contract, etc.)
- [ ] No hardcoded import statements (from backend.src.X)
- [ ] No trading-kit specific references
- [ ] All paths come from `config["paths"]`
- [ ] Templates use Jinja2 variables for paths
- [ ] Documentation shows multiple project structures
- [ ] Passed three-structure mental test
- [ ] Grep checks return no results

---

## 🎯 Goal

**Make it so anyone can:**

1. Copy `.agents/model-generator/` to their project
2. Create `.model-generator.yaml` with their paths
3. Run `generate.py` and get working code

**Without touching a single file in the skill directory.**

---

## 📝 Summary

| Rule | Example | Why |
| --- | --- | --- |
| Use `config["paths"]` | `config["paths"]["database_models"]` | Different projects, different structures |
| Dynamic imports | `{{ db_models_import }}.enums` | Import paths derived from file paths |
| No hardcoded paths | Never `"backend/src/api"` | Assumes specific structure |
| No project names | Use `{{ config.project.name }}` | Generic templates |
| Test 3 structures | Backend-only, monorepo, full-stack | Ensures true agnosticism |

**Remember:** We're building TWO things:

1. **Trading Kit** (project) - Uses the skill
2. **Model Generator** (skill) - Reusable tool

Keep them separate. Keep the skill pure.
